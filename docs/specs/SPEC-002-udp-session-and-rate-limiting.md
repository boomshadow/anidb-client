# UDP Session and Rate Limiting

AniDB's UDP API is unusually unforgiving: it is an unordered datagram protocol with a session, and the penalty for talking to it too fast is a temporary IP ban rather than an error reply. This spec describes how the library holds a session open, matches replies to commands, and paces itself so that a caller cannot get itself banned by accident.

## The session

A session is opened lazily and held for the life of the client. Authentication sends the account credentials together with a **client identity** — a registered name and integer version pair. AniDB refuses to authenticate an identity it does not know, so an application embedding this library registers its own and supplies it at init time (SPEC-006). The identity is held per transport rather than read from module state at send time, so an embedding application authenticates as itself without mutating global state.

When an encryption key is configured the session is established in two steps: an encryption handshake first, then authentication inside the resulting AES-encrypted channel. A configured key makes encryption mandatory — an attempt to authenticate unencrypted while a key is set is refused rather than silently falling back to plaintext.

Only a small set of commands may travel before a session exists — authentication, the encryption handshake, and the keepalive. Any other command sent without a session is refused rather than being sent and rejected by the server.

### When authentication does not succeed

A handshake has two outcomes, not one. Treating it as a signal that can only ever say *it worked* is what turned a refusal into a hang: the sender waited on a flag that a refused login had no way to set.

**Success is recognised by a whitelist.** Only the codes that mean the handshake worked — and that carry the field the handshake produces, a session key or a salt — reach the handlers that record it. Anything else fails the attempt. The alternative, a list of the codes that mean failure, is the one that cannot be kept complete, and when it was incomplete a refusal fell through to the success handler and raised there, on a thread where nothing could see it.

**Every attempt settles.** Refused, unanswered, or answered with something unrecognisable — each ends the attempt and releases whoever waited on it. An attempt that ends without settling leaves the sender parked on a reply that has already been and gone, and leaves the client believing a handshake is still in flight, so every later attempt declines to start.

**Whether to try again is decided from the response code, and defaults to no.** A code that says the server is unhappy — busy, out of service, banning this client for now — is temporary, so it registers a back-off and a later attempt may be made. Everything else is a refusal of these credentials or this client identity: a wrong password, an unregistered client, an encryption type the server does not offer. Those are **latched**, and no further authentication is sent for the life of the client. Retrying credentials AniDB has already rejected cannot succeed, and is a good way to turn a refusal into a ban.

**A retryable failure is paid for on the sender's thread.** The listener reports the failure and returns to reading the socket; it does not start the next attempt, because starting one means sending, and sending means waiting out the back-off. The next command that needs a session drives the next handshake, and waits there — where waiting costs nothing. A client with nothing queued does not authenticate at all, least of all into an API that has just asked it to back off.

Closing the client logs out cleanly, waiting up to the transport timeout for the server to acknowledge. A client that was never authenticated simply closes its socket.

### Keeping the session alive

Two idle-driven behaviors keep a session usable:

- When the authenticated address AniDB reports back differs from the local port, the client is behind NAT and sends a periodic keepalive to hold the mapping open. That address is **advisory**: AniDB only returns it when authentication asked for it, so a reply that omits it, or carries something that is not an address and port, means NAT was not detected — not that the login failed. A login that succeeded on the wire must not be undone by the check that was only advising it.
- After a long idle period the client sends a harmless command to refresh the session rather than discovering on the next real request that it has expired.

### Losing the session

The server can end a session at any time — through expiry, through an encryption session timing out, or by returning a code that says the session is no longer valid. Every one of those is handled the same way: re-authenticate, then re-send the command that discovered the loss, at the front of the queue so the caller is not made to wait behind unrelated work.

That recovery is itself a send, so it happens only when sending is allowed. If a back-off is open (see *Backing off*), the command that discovered the loss fails immediately, naming the back-off, rather than being held until the window closes. Recovering a session is not more urgent than being quiet.

The exception is a logout that discovers the session is already gone. There is nothing left to do, so the client simply shuts down.

## Correlating replies to commands

UDP guarantees no ordering, so a reply carries a tag naming the command it answers, and that tag is the only thing tying the two together. Tags cycle through a fixed range and are handed out under a lock, because commands are queued from several threads at once — the caller's thread, the sender, and the listener re-queueing after a loss. Two commands sharing a tag would cross one command's reply onto the other's callback.

A reply arriving with no tag at all is not a reply to anything: it is the server volunteering something, and in practice it is a ban notice. Those are read for their response code and acted on directly.

**Which codes those are is a property of the code table, not of the transport.** Every response code carries a *disposition* alongside its payload shape — ordinary, back off, or banned — recorded once beside the code it belongs to. The transport reads that disposition; it does not keep its own list. The transport used to restate the set as a literal tuple of integers, and the restatement disagreed with the table: the code AniDB actually answers with when it has had enough of a client was mapped to a response class and missing from the tuple, so the one reply that says *stop* was logged as unrecognised while the client kept sending. A classification that lives in one place cannot disagree with itself.

**Every reply is classified before its tag is consulted.** A refusal is a statement about the connection, not about whichever command it happens to carry the tag of, so it closes the gate whether it arrives untagged, correctly tagged, or tagged with something nothing is waiting on. Deciding from the tag first made a refusal's effect depend on a field that has nothing to do with what it means: an untagged one was read from the table and acted on, and a tagged one was matched to a command and handed to its caller as an ordinary success — no ban registered, no back-off opened, and the sender still firing. AniDB's own documentation notes that its ban code sometimes carries the wrong tag, so all three shapes are reachable in practice, and the one that was handled correctly was the least likely of them.

A refusal still **settles the command it answered**, so closing the gate never strands a caller. Where the tag matches nothing there is no caller to settle; where it matches a handshake, the handshake's own path settles it — which is also why the ban is registered there and not twice.

An untagged code the table does not know is logged and moved past. It is not guessed at, and in particular it is not assumed to be a ban.

Each matched reply's callback runs on **its own thread**, so a slow callback cannot stall the receive loop behind it. That this does not grow without bound is a consequence of the pacing below: replies cannot arrive faster than commands go out. A fixed worker pool was considered and rejected — a callback that waits on another reply would deadlock against a bounded pool, and the unbounded form has no such failure.

## Shared state across threads

The transport runs two threads of its own — one sending, one listening — and is called from whatever thread the application uses. Every piece of state written by one and read by another is reached through an accessor that takes a lock, rather than being touched directly.

- **The table of commands awaiting a reply**, inserted into by the sender and read, popped and iterated by the listener. Iterating a dict another thread is inserting into raises, and raising here ends the listener — after which nothing reads the socket and every caller waits on a reply that can no longer arrive.
- **The session key**, written when authentication succeeds and cleared when the session is lost. Code that tests it and then uses it must read it *once*: testing that a session exists and then reading it again to authorize a command lets the session be cleared in between, and the command goes out authorized with nothing.
- **The cipher** for an encrypted session, established by the encryption handshake and dropped with the session. It is cleared in the same critical section as the session key, because a half-cleared pair is either a command encrypted with a key the server has forgotten, or an unencrypted command on a session that requires one.
- **The handshake in flight**, created by whichever thread starts an attempt and completed by whichever thread learns its outcome — the listener on a reply, the listener's timeout sweep on silence. It is what makes *settled* distinguishable from *succeeded*: a flag can only report success, and this carries the failure too. Both the check and the settle happen inside the lock, so two threads reaching a conclusion about the same attempt cannot both act on it — the loser finds an attempt already settled and leaves it alone. The settled attempt then **stays in place**: a waiter arriving after it ended has to be able to read *why*, and clearing it left that waiter with nothing to look at, so it reported that the handshake had not completed instead of the refusal or the back-off that actually ended it — and its caller was retried instead of told. A genuinely new attempt replaces it, so a fresh attempt started by one thread is never completed by a reply belonging to the last one.
- **The latched authentication failure**, set once when a refusal is final and read before any attempt starts. It is the thing that stops the client re-offering credentials AniDB has already rejected, so a torn read of it is a client that keeps asking.
- **The pacing counters** — the burst allowance, the last-send time and the ban multiplier — every one of which is read-modify-write, and which the sender and the listener touch at the same time.

That last lock is **never held across a sleep**. The only sleep left is the pacing delay between commands, measured in seconds, and it is taken outside the lock — a sender paused between commands must not be able to stop the listener reporting a ban.

The sender **does not poll for work**. It waits to be woken when a command is queued. It does wake on a timeout as well, but only because the idle keepalives above are driven by "has enough time passed", which no notification can express.

The listener is started by the transport **once the transport has finished constructing itself**, not from the listener's own constructor. The listener calls back into the transport — to report a ban, to trigger re-authentication, to re-queue a command — so starting it any earlier exposes it to attributes that do not exist yet, on a thread where the resulting failure is invisible and fatal.

## The source address

AniDB meters and bans by the address a datagram arrives from, and a UDP source address is a host **and a port**. The outgoing source port is therefore not an implementation detail of the socket: it is half of the identity every rule in this spec is written against. A client that changes it changes who AniDB thinks it is talking to, and a client that shares it stops being able to tell which replies are its own.

Two rules follow, and both are about the transport having exactly one identity on the wire.

**The port is stable.** A client sends from one port for as long as it exists, and by default that is the same port for every client in every process on the host (SPEC-006 states the default; ADR-007 records the decision and the incident behind it). A port chosen afresh each time a client is built presents one host as a stream of distinct clients — which is what flooding looks like from the service's side, and which no single well-behaved process can see itself contributing to.

**The port is not shared.** The socket is bound so that a second client attempting the same port fails immediately and says so, rather than succeeding and having the host split the incoming datagrams between the two. A client receiving an arbitrary half of its replies looks, to itself, exactly like a client being ignored: it times out, it retries, and it trips the silence gate above — for a refusal that was never AniDB's.

The address AniDB reports back on a successful authentication is the only outside confirmation that either rule is holding; *Keeping the session alive* says what that address is, and *Reading the transport's state* says how it is read.

## Pacing

The pacing policy is the thing that keeps a client out of trouble, so it is stated here explicitly rather than being inferable from whether a request happened to go out.

- A short opening burst of commands is allowed at a faster interval; after that burst is spent, a slower steady interval applies. This mirrors AniDB's documented flood protection, which permits a burst and then requires roughly one command every four seconds.
- Time the application spent on its own work counts toward the interval. An application that is slow in its own right is not paced twice.
- After a long enough quiet period the burst allowance is considered fresh again, because the server's own flood counter has decayed by then too.

A caller cannot send faster by asking. There is no override.

**The limiter is replaceable, and the policy is not.** The object holding this policy may be supplied by the embedding application (SPEC-006), and what that buys is *lifetime* rather than latitude: everything the limiter knows is per-process, so a restart forgets the burst allowance, the last send, and any back-off that was standing. Supplying one is how an application keeps that across restarts. It is not a way to pace faster — the intervals above are the class's, and a limiter that reported a shorter back-off than it was given would be lying to the transport rather than configuring it.

What may be resumed is a standing back-off, how far it has doubled, which refusal opened it, and how long ago the last command went out. Each is expressed as a duration rather than an instant, because these are measured on a monotonic clock whose zero point does not survive the process; SPEC-006 covers that and the states that are refused as incoherent.

## Backing off

A ban, a server-busy reply, or a network send failure puts the transport into a backed-off state. The back-off starts at roughly the length of an AniDB temporary ban — retrying sooner is pointless — and doubles for each consecutive ban, up to a ceiling.

The ceiling exists because the doubling compounds when it is *authentication itself* that keeps failing. Unbounded, that sequence walks off into delays measured in days: a client that has, for practical purposes, stopped, while reporting only that it is waiting. In the ordinary banned-then-readmitted cycle the multiplier rarely leaves its first step, because a successful authentication clears the back-off entirely.

**A back-off is a window during which nothing is sent. It is not a sleep.** Nothing waits it out; the sender asks whether the window is still open and declines to send if it is. That distinction is the whole of it:

- **The listener keeps reading.** The back-off used to be taken inside the send path, and the listener reaches that path too — through an untagged ban notice, and through its own timeout sweep. So the thread whose only job is to read the socket could spend hours not reading it. Every reply arriving in that window was lost, and nothing could time out either, because the sweep runs on that same thread.
- **The caller is told, not held.** A command that arrives while the window is open fails immediately, naming the back-off and how much of it is left. Half an hour of silence towards AniDB is correct; half an hour of blocking towards a caller is the reported incident.
- **Nothing goes out at all** — not the command, and not the authentication it would have triggered. The sleeping version still *intended* to send, and did, the moment the clock allowed it. Waiting is not the same as being quiet, and being quiet is what AniDB is asking for.

**Reaching the end of the window does not clear the ban.** The multiplier stays until an authentication succeeds, so a client that comes back and is refused again backs off for longer rather than starting over. The first command after the window is, in effect, a single probe: it succeeds and the back-off is cleared, or it fails and a longer window opens. There is never a burst on recovery, because the sender sends one command at a time and the first one it must send is the handshake.

**The window is jittered.** Clients banned together must not return together. The herd here is close to home: several short-lived processes on one host, each authenticating for itself, banned within seconds of each other. Without jitter they come back in step, which against a service that counts requests per client is a burst. The jitter keeps a floor and randomises the remainder rather than picking uniformly from zero — a client that rolled low would come back almost immediately, which is the one thing not to do.

### Silence is a refusal

AniDB's *primary* enforcement is not a response code. It stops answering: datagrams from a banned client are dropped, and nothing comes back to say so. A transport that waits to be told it is banned is therefore never told, and it keeps sending for as long as its caller keeps asking.

So absence of traffic is a ban signal in its own right. The transport tracks when a datagram last arrived from AniDB — **any** datagram, of any kind: a reply to some other command, an untagged notice, even a packet it cannot parse. All three say the same thing about the connection, which is that something is still coming back. Alongside it, the transport tracks how many commands have gone unanswered in a row since then.

The gate closes when a command times out, nothing has arrived from AniDB since before that command was sent, and the run of such timeouts reaches a small threshold. The threshold is not one, because one is ordinary: UDP loses datagrams, and absorbing a lost one is what the retry budget exists for. A run of them with nothing at all coming back is not loss.

A handshake is not counted towards that run. It never retries — an unanswered authentication backs off on its first timeout, by itself — so it needs no detector, and feeding it into one would register a single silence as two bans and double the back-off for it.

**The gate outranks the retry budget.** A timed-out command is ordinarily re-sent, and against a lost datagram that is right. Against a service whose way of saying no is to ignore packets, every remaining attempt is more traffic into the thing doing the banning. Once the gate is closed the command is not sent again: it fails, and it fails with the reason, so its caller learns that the transport is backing off rather than that one request happened not to come back.

### What a refusal says

A back-off is opened for three different reasons, and a caller handed one can only act on it if it can tell them apart:

- AniDB **refused** this client, with a response code that says so.
- AniDB has gone **silent**, and the ban carries no code because there was no reply.
- The datagram never left this host at all — a **local** failure, nothing asked of AniDB, and a back-off this client imposed on itself rather than spin on a socket that is not working.

Which one it is, and how long the window has left to run, are carried as **data on the refusal** rather than only as words in its message. The message alone did not survive being read by a program: it rounded the remaining time to whole minutes, so a fifteen-second back-off read as *0 minutes*, and it said nothing about the cause at all — leaving a caller to choose between parsing English and treating every refusal identically. The remaining time is stated in seconds and unrounded.

What the exception hierarchy already distinguished stays distinguished: a ban clears on its own and the request is worth making again, while a refusal of these credentials or this client identity is latched and needs a human. The added data says *which* refusal, not whether to retry.

A latched refusal carries the response code it was refused with, for the same reason: *the login failed* and *this client version is no longer registered* both need a human, but not the same human doing the same thing. One is a credential to correct and the other a registration to renew, and a caller that can only read the message string cannot route them differently.

## Timeouts and retries

Every command in flight is watched. When one goes unanswered past the transport timeout:

- If replies from the server have arrived more recently than this command was sent, the API is alive and something else is happening — most likely a re-authentication in progress. The command is re-queued at the front.
- If the command has no send time at all, it was re-queued while the sweep was running and has not gone out again. It has not timed out, so it is re-queued rather than retried — the sweep collects expired commands and claims them in two passes, and a re-queue landing between the two is expected rather than exceptional.
- Otherwise the command has genuinely timed out. It is retried, up to a fixed number of times *in total*.

**The budget is spent, not renewed.** When it runs out the command fails: whoever asked for it is told no reply is coming, and the transport backs off before anything else goes out. There is no branch that restores the allowance and tries again, because that is not a retry policy — it is an unbounded loop with a growing interval. It was the previous behaviour, and it is the reported hang: a command AniDB would never answer was re-sent for the life of the process while its caller waited on a signal that only success could send.

What the budget bounds is **how many times the command reaches AniDB**, not how many times it goes round the queue. A service that bans clients for asking too often counts requests.

**The budget is a ceiling, not an entitlement.** The silence gate can end the retries earlier, and against total silence it does — the budget is sized for a lost datagram, and silence is not loss. Whichever of the two stops first is the number of times the command reaches AniDB.

The caller is told *before* the back-off starts, in that order. The decision to give up has already been made; delivering it after a back-off would hold the caller for half an hour or more to hand over an answer that was ready immediately.

Every interval the transport measures — how long a command has been in flight, how recently a reply arrived, how long to pace or back off — is read from a **monotonic** clock rather than the wall clock. The wall clock can be stepped by a time sync or an operator: a backward step makes every command in flight look newly sent, and a forward step expires them all at once.

Authentication and the encryption handshake do not retry this way. A timeout on either means the API is not answering at all, so the transport backs off immediately rather than re-sending credentials into silence — and it settles the handshake, because a sender waiting on an authentication is waiting on something that now has an answer, even if the answer is silence.

## Every request has an outcome

A command carries its result to whoever asked for it, and that result is *either* the reply *or* the reason there will not be one.

A callback cannot do this. There is no callback for a reply that never arrives, so a caller with only a callback cannot tell "AniDB says there is no such thing" from "we were banned and gave up" — and on the second it has nothing to wait for. Both are answers; only one of them was reaching the caller.

- A reply settles the command **after** its callback has run, so a caller released by the outcome finds the callback's work — the cache write — already visible.
- A callback that raises fails the command. A reply that arrived and was then mishandled is still no answer, and it used to be *less* visible than one that never came: the handler ran on a thread nobody joins, so the exception was invisible at the time and the caller waited anyway.
- Retrying reuses the same outcome. The caller is waiting on the request, not on any one attempt at it.
- **When the transport concludes it cannot work at all, that conclusion reaches every caller it was working for** — everything queued and everything awaiting a reply fails, and requests made afterwards fail immediately rather than joining a queue nothing will drain. A transport that stops silently is worse than one that stops loudly: every caller is left holding a request that can no longer be served and has no way to find out.

That last rule is what the listener-liveness check was always for. It read as *kill the main thread if the listener dies*, and what it actually did was raise on the **sender** thread, ending the one thread that could have told anybody. Both threads then being gone, the queue stopped draining, every command in it had no send time — so the timeout sweep skipped it — and every caller waited on a reply that could not be read even if it arrived.

## Reading the transport's state

An application embedding this library has to be able to tell *quiet because there is nothing to do* from *quiet because AniDB has closed the gate* — and to tell them apart without sending anything, sending being exactly what a banned client must not do, and without reaching into private attributes, which is exactly what a library must not require of its callers.

So the transport answers, read-only and out of state it already keeps: whether a ban stands, which of the three refusals opened it, how long the window has left, how far the back-off has doubled, how long the current session has been up, and the address AniDB last reported seeing this client arrive from.

**The transport is reachable to be read.** The library hands out the object carrying that surface, alongside the accessor that hands out a cache session. A surface a caller can only reach through a private attribute is not a surface; promising one and then withholding the means to obtain it would make this section's claim untrue for every caller that configures the library the ordinary way. A client configured for cache-only work has no transport at all, and asking for one says so rather than answering with nothing.

**Reading is what that accessor is for; it is not the way to send.** This needs saying because the object handed out is a whole transport and its send path is reachable through it, so the boundary is one a caller can cross without noticing — and did. What an embedding application legitimately needs is not the ability to send arbitrary commands but two specific things, and both have their own entry point: reading the state above, and establishing the session at startup rather than on the first request, which is `connect()` in SPEC-006. Anything else that talks to AniDB goes through the object layer (SPEC-001), which exists so that a caller's reads are answered from the cache rather than from the socket — that being the whole of how this client stays under the limits this spec is written about.

**Building a command by hand is not a supported entry point.** `commands.py` transcribes AniDB's command set for this library's own use; it is not part of the declared surface, and a caller reaching for it is working around a missing call rather than using an interface. If some legitimate need has no entry point, the answer is to give it one — as `connect()` was — not to widen this into a general-purpose command channel that bypasses the cache.

That last one is worth stating separately, because it is the only outside confirmation of something the client cannot otherwise observe: which source address AniDB is counting its requests against. AniDB returns it only when authentication asks for it, and it stays advisory — a login that succeeded on the wire is not undone by its absence (see *Keeping the session alive*) — but when it is there, both halves of it are kept. It used to be parsed for its port, compared, and discarded, which threw away the half that identifies the client.

## Stopping

A transport that is stopped ends both of its threads, releases its socket, and fails whatever was still in flight. All three, on every path — which was not previously true of any path.

**Logging out is a courtesy; ending is not.** Stopping used to be a choice between the two and did half the job either way. Authenticated, it sent LOGOUT, waited for the acknowledgement and returned — without ever closing the socket, so the listener went on reading a port nobody could take back. Unauthenticated, it closed the socket and never signalled the sender, which went on waking on its idle tick forever. So the logout is attempted where there is a session to end, and the teardown runs regardless of how that went. The wait for the acknowledgement is bounded, and the bound can be shortened by the caller: a client AniDB has stopped answering will never be told its logout arrived, and holding an application's shutdown open for the full command timeout to discover that is the wrong trade.

**Nothing is sent on a teardown that has no session to end.** A client that never authenticated has nothing to log out of, and a client in a back-off must not send at all — that is what the back-off *is*. A courtesy packet from either is worse than silence.

**Releasing the port takes more than closing the socket.** A thread blocked in a receive call keeps the socket alive in the kernel until that call returns, so the bound port survives the descriptor being closed. With an ephemeral, shareable port that is invisible. Here the port is pinned and not shareable (ADR-007), so a listener still sitting in its receive call holds the only port the next client may use, for as long as its socket timeout lasts — a failure that looks exactly like the unrelated one it is not. So the receive loop is signalled, then *woken* — by a zero-length datagram the client sends to its own address on loopback, never to AniDB — and waited for, and only then is the socket closed. `close()` promises the port back (SPEC-006); this is what makes that true at the moment it returns rather than some seconds later.

**The waits are bounded.** Each thread is woken rather than merely signalled, so in the ordinary case they leave in moments. The bound exists so that a thread wedged somewhere unexpected slows a shutdown down instead of preventing one, which is the containment rule below applied to shutting down: a library does not get to hold its host process open.

**Everything outstanding is failed.** A command in flight when the transport stops can never be answered now, so it is settled with the reason rather than left registered. That is *a waiter is always released*, applied to the one path that used to ignore it.

## Failure containment

Two rules bound how badly the transport may fail, both learned the hard way:

**A library never terminates its host process.** An unparsable reply, an unrecognised untagged response, or a failed cache fetch is logged and moved past. Neither the transport nor anything below it exits the interpreter — and in a non-main thread an attempt to do so would end only that thread, leaving the socket unread and every caller waiting on a reply that can no longer arrive.

**A waiter is always released.** Every path that can end a fetch — success, a not-found reply, an unguessable object, an exception mid-parse, a refused or unanswered handshake — releases whoever is blocked on it. A code path that returns early without doing so is a permanent hang, not a lost result.

Releasing is not the same as succeeding, and the two must be distinguishable. A signal that can only say *done* cannot report a failure, so the waiter cannot tell "there is no answer" from "the answer never came" — which is why the handshake carries its outcome rather than a bare flag.

- **Line of truth (external):** the AniDB UDP API definition, which owns the command grammar, response codes, the flood-protection thresholds this spec paces against, and the guidance to select one fixed local port above 1024 and reuse it. `src/anidb_client/commands.py` transcribes the command set and its parameter-combination rules; `src/anidb_client/responses.py` transcribes the response-code table.
- **Related specs:** SPEC-001 (the object layer whose attribute reads trigger these fetches); SPEC-003 (the cache that exists to keep this transport idle); SPEC-006 (credentials, the encryption key, the client identity and the outgoing port).
- **Tests:** pacing and back-off are tested against an injected clock, sleep and jitter roll in `tests/unit/test_ratelimit.py`, so a half-hour window is asserted in microseconds and exactly: that a ban is never slept, that the window reflects the multiplier, that elapsing does not clear the ban, that the jitter varies the window and never shortens it to nothing, and that the pacing lock is not held across the one sleep that remains. `TestBackingOffWithoutSleeping` in `tests/integration/test_link.py` drives the same policy through the real transport with a limiter that genuinely sleeps -- a fake one cannot tell sleeping from not sleeping -- and pins that the listener keeps reading while a back-off runs, that nothing reaches the wire during it, and that a caller is told in moments rather than held for the window. Thread safety and thread lifecycle are covered in `tests/integration/test_link.py`: `TestSharedTransportState` for the locked session and cipher accessors and the fact that they are cleared together, and for the two handshake items alongside them — two threads racing to settle the same attempt, where exactly one may win and the loser must find the attempt already settled and leave it alone -- still readable, so a waiter arriving afterwards learns why it ended; settling an attempt that has already gone; and the latched refusal being read under the lock, so no attempt starts after it; `TestListenerStartup` for the listener not starting itself and the transport starting it once built; `TestSenderWakeup` for a queued command being dispatched without waiting for the idle tick, timed across enough round trips that a polling sender would be unmistakable; `TestCallbackIsolation` for a blocked callback not stopping the next reply being read; and `TestListenerRobustness` for the listener surviving garbage, an unrecognised untagged code, and a command re-queued midway through the timeout sweep — the garbage case also pins settlement on that path, because surviving the packet is only half of it: the handshake the garbage answered has to settle too, or nothing can start another one. `TestCommandOutcome` in `tests/integration/test_link.py` covers the outcome a request carries: a reply settling the command that asked for it, the callback having finished before the outcome arrives, a command that is never answered failing its caller rather than hanging it, the bounded number of times such a command reaches the wire, and a callback that raises failing the command instead of stranding it. Command construction and its parameter validation live in `tests/unit/test_commands.py`, where `TestRetryPolicy` pins that the attempt budget is spent rather than renewed, that the caller is told before the back-off begins, and — driven through the same counting the transport does — that a command retried to exhaustion terminates after a fixed number of sends; response parsing and the code table in `tests/unit/test_responses.py` and `tests/unit/test_response_field_selection.py`. `TestDisposition` in `tests/unit/test_responses.py` pins the classification each code carries, including the whole set of codes that must stop the client, so losing one is a test failure rather than something only AniDB notices. `TestBanHandling` in `tests/integration/test_link.py` drives the codes that arrive *untagged* through the listener as real unsolicited replies, and `TestTaggedRefusals` beside it drives the same codes in the other two shapes — carrying the tag of the command they answer, and carrying a tag nothing is waiting on — pinning that each closes the gate and that the first also settles the command it answered. `TestSilenceIsABan` covers the refusal that arrives as no packet at all: that one unanswered command is not silence, that the gate closes at the threshold, that any datagram resets the run, that a handshake is not counted and neither is a command that timed out while replies were arriving, and end to end that total silence closes the gate and stops the retries short of the attempt budget. `TestSilenceOverridesTheBudget` in `tests/unit/test_commands.py` pins the same override at the level of one command: not re-sent, failed with the reason, gate closed. `TestBanCause` in `tests/unit/test_ratelimit.py` pins which of the three refusals the window records, that it survives the window elapsing, and that a successful authentication clears it with the ban. `TestResumingStateFromAPreviousProcess` and `TestIncoherentStateIsRefused` in the same file pin the limiter a caller may supply: that a standing back-off, its multiplier and its cause come back, that the window is measured from now rather than from a stored instant — asserted across two clocks reading wildly different numbers, which is the failure a stored deadline would cause silently — that a resumed multiplier makes the next ban longer, that everything seedable can also be read back, and that a back-off without a multiplier, a cause without one, a multiplier without a cause, a multiplier past the ceiling and negative durations are each refused rather than quietly repaired. `TestHealthSurface` in `tests/integration/test_link.py` pins what an embedder can read without sending anything — ban state, cause, unrounded remaining time, multiplier, session age, and the reported address in both the presence and the absence of the field AniDB only sometimes returns. `TestFailedAuthentication` in the same file covers the tagged half: every code AniDB can refuse a handshake with settles rather than parking the sender, a rejected credential is never offered a second time, a ban is retryable where a rejection is not, and an unanswered handshake settles like a refused one. End-to-end session behavior runs against the fake server in `tests/fake_anidb.py` from `tests/integration/test_link.py`. `TestTheSourcePortIsPinned` in `tests/integration/test_link.py` pins the socket's identity: that the port a link is given is the port it binds, and that a second bind of a port already held fails loudly with an error naming it, rather than succeeding and splitting one client's replies between two processes. `TestFailedAuthentication` also pins that a latched refusal carries the code it was refused with, across every code AniDB can refuse a handshake with, and `tests/unit/test_get_link.py` pins that the transport is reachable through the public accessor and that asking for one that does not exist says why. `TestConnectingOnDemand` in `tests/integration/test_link.py` covers the transport's side of establishing a session on purpose: that it authenticates once, that calling it again does not authenticate again -- the property that keeps it from being a way to get banned -- that four callers racing it produce one handshake between them rather than four, which is the case the idempotence rests on that only appears under load, that it is not re-authentication, which logs in again deliberately, that a refused credential and a latched refusal are raised without the credential going out a second time, that a standing ban is raised with nothing reaching the wire at all, and that a handshake nobody answers fails rather than hanging its caller's startup. `TestStoppingTheTransport` in `tests/integration/test_link.py` covers what stopping has to achieve and used to achieve only half of: that the source port is bindable again the moment `stop()` returns, from both the authenticated and the unauthenticated branch; that both threads have ended; that a teardown with no session to end reaches the wire with nothing, and that an explicit no-logout teardown does the same even when there is a session; that a logout AniDB never answers still tears the transport down, within the time it was given rather than the command timeout; that stopping twice is safe; and that a command in flight is failed rather than stranded. The library-level half — that `close()` gives the port back, in the same process and with no waiting — is in `tests/unit/test_lifecycle.py`. The HTTP-side timeouts are covered in `tests/unit/test_http_timeouts.py`. The waiter-release guarantee is pinned from the response-handling side in `tests/unit/test_file_response_decoding.py`, where a reply that parses but cannot be decoded must still release everything waiting on it, and in `tests/unit/test_enum_converters.py`, where an ANIME or GROUP reply naming a relation the library cannot read must do the same.
